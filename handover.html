What it does

Every Shopify store on the list is watched each night — 242 of them today — and the system records what changed: a price moved, a variant sold out, a product left the store, a product came back. The result is a dashboard where you can pick any store, any product, any variant, and read its whole price and stock history day by day.

It is built in two halves that meet in exactly one place — a folder of CSVs on Google Drive. Learn that folder and each half can be understood on its own.

Phase 1 — collecting it

Three UiPath robots on a Windows VM, coordinating through one Google Sheet. They ask every store for its own product feed, find each store's 20 best sellers, and file the day's day’s CSVs into a dated Drive folder.

UiPath Studio · Google Sheets · Chrome · Google Drive. It knows nothing about the database.

Phase 2 — making sense of it

A Node service reads that folder and writes only the differences into Postgres, then serves them to a dashboard. A day's file holds ~600,000 rows for a large store and almost all are identical to yesterday, so 2.5 GB of CSV becomes about 150,000 rows.

Node · Express · PostgreSQL · Vercel. It knows nothing about UiPath.

Adding a store is one row. Put its URL in a new Sheet1 row with the next Store_ID and leave the status columns blank — blank means "still to do", so Bot 1 picks it up on its next run and Bot 2 follows. Nothing on the VM, in Orchestrator or on the server needs changing. Phase 2 learns about it from the CSV that then appears. 242 is simply today's count, not a limit.
Why "Fail or empty" is the queue. A blank cell is a store that has never been done today; Fail is one that was tried and did not work. Both need doing, so both filter the same way, and a run that is interrupted simply resumes — nothing has to remember where it stopped.

What was measured, not guessed

Every store on the list was probed once, gently, before this was written — one request each at limit=1, 900 ms apart. Of the 251 on it that day, 234 answered with JSON, and not one returned 429 or 500.

So the 429s and 500s in a live run are caused by the pace of the run, not by the stores — which is what the delays above are for.

The other 17 will never answer at any pace, and are told apart on purpose so they are not retried for nothing:

The CSV is a reproduction. The 49 columns, their order, the quoting, the LF endings with no BOM and no trailing newline — all read out of shopify-scraper.com's own bundle so the file is byte-identical to the one the site exports. That is why Phase 2 could switch to this without changing a line of its parser.

Bot 2 · Bot_2_BrandSearch 06:00 AM

Finds each store's 20 best sellers, then goes back into the CSV Bot 1 already wrote and marks them. Two workflows, one after the other.

Why the handle and not the name. Product names repeat heavily — 45 different products on one store are all called "RTS | SHIRT". P2

Phase 2 — Turning it into a tracker

From the Drive folder onwards: one night and one page view, step by step. Everything from here down is Phase 2.

Why step 5 is the whole design

A large store's file holds 600,000 variant rows, and on a normal day almost every one is identical to yesterday. Storing them all would mean 4 million rows a night and a database nobody could query.

So each variant keeps one row holding its last known state (variants.current_*), and the file is compared against that. Same → nothing happens. Different → one history row, which also records what the value was. 2.5 GB of CSV becomes roughly 150,000 rows.

That is also why the history reads plainly: every row is a real event, not a daily snapshot someone has to diff themselves.

What counts as "different"

newfirst time this variant has been seen
price_up
price_down		the selling price moved
discount_changethe compare-at ("was") price moved
stock_out
stock_in		became unbuyable / buyable again
removedgone from the store's feedNot the same as out of stock — it may well have had stock when it left
relistedcame back into the feed

Architecture

Three pieces in two places. The browser never talks to the server directly.

Why the doorman? The server's API has no login of its own — it only checks a shared token. If the browser called it directly, that token would sit in the page source for anyone to read. The Vercel function holds it instead, so it never reaches the browser. It also bridges HTTPS (Vercel) to plain HTTP (the server), which a browser would otherwise block.

The two-layer design. variants.current_* is a cache of the latest known state. It exists so an ingest can diff today's file against one indexed row per variant instead of scanning 10 million history rows — and so the dashboard can answer "how is this store now" instantly. It is rebuildable from history at any time, which is exactly what a rewind does.
Why replaying an old day is refused. Because that cache holds the newest values. Feeding it a file from three days ago produces differences that never happened. Only a store's most recent day can be re-ingested; to fix an older gap you rewind forward days first, then replay in order.

Forgetting the build step is the usual mistake. public/ is the source but vercel-site/ is what deploys, so an edit that is not rebuilt and committed simply never reaches the site — and nothing errors. The build also stamps the stylesheet's content hash into the link, without which browsers hold yesterday's CSS against today's markup.

Order, when a change touches more than one

1 · server firstThe API deploys in about a minute, by hand
2 · then pushVercel picks it up automatically
Never the other way round. The pages go live within a minute of the push; the API only when you run the tar command. Push first and a live page calls a route its server does not have yet — a real 404 in front of whoever is looking at it.

The nightly job does all of this by itself. These are for the days it comes back short.

A · Putting a day in the two you need

1 — from a folder on this machine

npm run ingest:server                          today's folder, found automatically
npm run ingest:server -- --date 2026-09-05        a particular day
npm run ingest:server -- --dir "D:/backup/2026-09-05"   a folder somewhere else

Sends the CSVs over gzip, then runs the ingest on the server. Nothing can throttle it — use this whenever the folder is on your disk. It looks for E:\Project CSV\YYYY-MM-DD\ unless you say otherwise (CSV_BASE changes the root).

2 — from Google Drive, run on the server

npm run ingest:drive:server                    run it and watch
npm run ingest:drive:server -- --detach            start it and walk away ← use this for a full day
npm run ingest:drive:server -- --status            is it running? what did it say?
npm run ingest:drive:server -- --dry-run          list what it would do
npm run ingest:drive:server -- --date 2026-09-05  force the run date for every file

Nothing leaves your machine — the server reads Drive itself. But Google rate-limits it, so a full day has taken five hours and still arrived incomplete. --detach lets the server carry on alone; --status tells you where it got to.

Which to use. Folder on this machine → command 1, always. Not on this machine → command 2, and expect to run it more than once. A real day went 119 → 226 → 237 → 240 across four runs as the throttle eased.

B · A specific day that is missing

The most common job. Say 6 September never landed:

# 1 · what does the database actually have?
npm run ingest:drive:server -- --status

# 2 · is the folder on this machine? (E:\Project CSV\2026-09-06)
#     yes →
npm run ingest:server -- --date 2026-09-06

#     no  →
npm run ingest:drive:server -- --detach --date 2026-09-06

# 3 · check it landed — see section E below
Always pass --date when you mean a particular day. Left off, the command resolves the date itself, and a wrong guess produces "240 already done" on a day you know is empty — no error, nothing written.
Only the newest day can be re-ingested. Replaying an older one is refused on purpose: variants.current_* holds the latest values, and diffing a three-day-old file against them invents changes that never happened. To fill an older gap, see section D.

D · Undoing a day, and filling an older gap --rewind

node scripts/ingest.mjs --store 3 --date 2026-09-09 --rewind

Deletes that store's run for that date — the history rows, the run record, the counts — and rebuilds variants.current_* from the history that remains. Nothing else is touched.

Filling a gap in the middle

If 7 September is missing but 8 and 9 are in, you cannot simply add 7 — the current-state cache is already at the 9th. Walk it backwards, then forwards in order:

# 1 · rewind the days that came after, newest first
node scripts/ingest.mjs --store 3 --date 2026-09-09 --rewind
node scripts/ingest.mjs --store 3 --date 2026-09-08 --rewind

# 2 · replay in order, oldest first
node scripts/ingest.mjs --store 3 --date 2026-09-07 --file …/2026-09-07/store3.csv
node scripts/ingest.mjs --store 3 --date 2026-09-08 --file …/2026-09-08/store3.csv
node scripts/ingest.mjs --store 3 --date 2026-09-09 --file …/2026-09-09/store3.csv
This is exactly how store 3's missing 7–8 September was recovered. Order is not optional: a day replayed out of sequence compares against the wrong "current" and writes changes that never occurred. Take a backup first if the store is large.

7

Things that will bite you

Every one of these cost real time to find. They are written down so they cost you none.

The folder's name is the date — never a file's timestamp

The scrape writes each CSV the evening before it is filed, so a folder named 2026-09-04 holds files stamped 2026-09-03. Trusting the timestamp files a whole day under the day before — and because that day is usually already ingested, every store reports "already done", nothing is written, and nothing looks wrong.

Google's rate limit arrives as a 403, not a 429

Drive answers a throttle with an HTML page titled "Sorry…" under status 403 Forbidden. That reads like a permissions problem and is not one. The code tells the two apart by the body and retries only the throttle — 3s, 10s, 30s, 90s. A full day has still taken five hours and arrived incomplete; that is why command 1 exists.

A store that genuinely shrinks used to get stuck

If a feed comes back at under half the stored product count, removals are skipped — a short file is usually a bad scrape. But skipping removals is what keeps the stored count high, so it tripped again the next day, forever. One store sat in it for eleven days showing 1,093 products when it had 68. Now the count compares against products still listed, and the same small number three days running is accepted as the truth.

Large stores need headroom

The biggest store is 382 MB of CSV and 556,000 variants — close to Node's default heap ceiling. Files over 200 MB now run first and alone with a 3 GB heap. Three of them side by side does not fit in 7.9 GB.

Re-running is safe. Assuming is not.

Every command skips a store+date already recorded, so run them as often as you like. What you must not do is assume a day is in because something exited quietly — read the count. A whole folder reporting "already done" on a day you know is missing means the date was resolved wrongly.

Overnight, three robots ask every store on the sheet for its own catalogue, mark each store's best sellers inside the file, and drop the day on Drive under its date. At 11:00 a Node job reads that folder and writes down only what is different from yesterday. A dashboard on Vercel reads it back.
