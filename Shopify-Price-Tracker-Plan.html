01Project Flow

Google Sheet mein 100 store URLs. Har din har store se ek CSV. Us CSV se price, discount aur stock ki tabdeeli nikalni hai — variant level par (size / color), sirf product level par nahi.

1

Google Sheet se 100 store URLs parhta hai → har store ka CSV download karta hai → Google Drive par upload kar deta hai. Roz automatic.

Drive se nayi files uthata hai → CSV parse karta hai → sirf zaroori 18 columns nikalta hai → database mein daalta hai. Har file ka record scrape_runs mein rehta hai.
3
Phase 2 — Diff Engine
Aaj ka data kal se compare karta hai. Sirf jo badla wo history mein likhta hai — price up/down, stock in/out, naya product, hataya gaya product.
4
PostgreSQL

5
Frontend — Next.js
Login → 100 store cards → card par click → us store ki report (charts + variant table) → date range filter → PDF download.

03Database — Kaunsi Use Karni Hai & Kyun

Faisla: PostgreSQL (Relational). Vector DB bilkul nahi.

DatabaseFaislaWajah
PostgreSQL✓ Yehi use kareinNumbers, dates aur exact comparison — sab kuch perfect. Data already tables ki shakal mein hai.
MongoDB⚠ Zaroorat nahiChal to jayega, magar din-ba-din ka comparison khud manually likhna parega. Khwaamakhwa mushkil.
Vector DB✕ Bilkul nahiPrice ka farq pakarhta hi nahi. Neeche example dekhein.

Vector DB kyun nahi — asal example

Vector DB sirf ek kaam karta hai: "is se milta julta kya hai?" Wo text ko meaning ke hisaab se dhoondhta hai. Exact numbers compare nahi karta.

Aapki apni file se ek asli variant lein:

Kal :  SS-59.1-25-3-Blue  |  price 3,432  |  compare_at 4,290  |  in stock
Aaj :  SS-59.1-25-3-Blue  |  price 3,290  |  compare_at 4,290  |  out of stock

Yehi pakarna hai →  142 rupay kam, discount 20% → 23.3%, aur stock khatam
✕ Vector DB yahan fail ho jata hai

Dono lines ko embed karein to unke vectors ek doosre ke oopar aa jate hain — cosine similarity ≈ 0.999. Vector DB kahega "ye to same cheez hai." Usay 3,432 aur 3,290 ka farq samajh hi nahi aayega — kyunki dono mein wahi shirt, wahi color, wahi naam hai.

Doosra masla: vector search approximate hota hai (design hi aisa hai). Yani 100% guarantee nahi ke saare results mil gaye. Aapko roz report chahiye jis par log bharosa karein — agar 3 stores ki price drop miss ho gayi to report bekaar.

SQL mein wahi kaam

Ek line. Exact, poora, aur fast:

WHERE aaj_ka_price < kal_ka_price
SawalPostgreSQLVector DB
Kis product ka price gira?✓ Ek query✕ Na-mumkin
Kaunsa variant stock out hua?✓ Ek query✕ Na-mumkin
1 July se 27 July tak ki report✓ BETWEEN✕ Date ka concept nahi
Kaun se naye products aaye?✓ Ek query✕ Na-mumkin
"Isi jaisa product dhoondo"Mushkil✓ Behtareen
ℹ Aage chal kar Vector DB kab kaam aayega

Jab aap do alag stores ke same product ko match karna chahenge — jaise "Blue Printed Lawn 3-Piece" aur "3 PC Lawn Suit — Blue" (naam alag, cheez same). Lekin aapne khud kaha hai ke abhi stores ko aapas mein compare nahi karna. To filhal chhor dein.

Achi baat: Postgres mein pgvector already mojood hai — zaroorat pare to usi database mein on kar lena. DB badalne ki zaroorat nahi paregi.

06Database Schema

5 tables. Ek nazar mein poora structure:

stores            100 rows — har store ka ek
   │
   ├── scrape_runs    roz ek per store — scrape chala ya fail hua
   │
   └── products       ~2,000 per store · UNIQUE (store_id, handle)
          │
          └── variants   ~4 per product · size / color / fabric
                 │
                 └── variant_history   append-only · price + stock + date
                                     ↑ ye dil hai poore system ka

1 · stores

CREATE TABLE stores (
  id               BIGSERIAL PRIMARY KEY,
  name             TEXT NOT NULL,
  domain           TEXT NOT NULL UNIQUE,      -- alkaramstudio.com
  csv_prefix       TEXT,                       -- Drive file match karne ke liye
  active           BOOLEAN NOT NULL DEFAULT true,
  last_scraped_at  TIMESTAMPTZ,
  created_at       TIMESTAMPTZ NOT NULL DEFAULT now()
);

2 · scrape_runs — reliability ka sabse ahem table

CREATE TABLE scrape_runs (
  id              BIGSERIAL PRIMARY KEY,
  store_id        BIGINT NOT NULL REFERENCES stores(id) ON DELETE CASCADE,
  run_date        DATE NOT NULL,
  status          TEXT NOT NULL CHECK (status IN ('pending','success','failed','partial')),
  file_name       TEXT,
  rows_ingested   INT DEFAULT 0,
  products_found  INT DEFAULT 0,
  variants_found  INT DEFAULT 0,
  changes_found   INT DEFAULT 0,
  error_msg       TEXT,
  started_at      TIMESTAMPTZ DEFAULT now(),
  finished_at     TIMESTAMPTZ,
  UNIQUE (store_id, run_date)      -- ek din mein ek hi run
);
⚠ Ye table skip mat karna

Iske baghair pata hi nahi chalega ke kis store ka scrape fail hua. Banda purani data ko aaj ka samajh lega — aur khamoshi se fail hone wale scrapes hi wo cheez hain jis se daily-report system par se bharosa uth jata hai.

3 · products

CREATE TABLE products (
  id             BIGSERIAL PRIMARY KEY,
  store_id       BIGINT NOT NULL REFERENCES stores(id) ON DELETE CASCADE,
  handle         TEXT NOT NULL,            -- UNIQUE ID — title nahi!
  title          TEXT,
  vendor         TEXT,
  product_type   TEXT,
  tags           TEXT[],
  published_at   TIMESTAMPTZ,
  status         TEXT,
  image_src      TEXT,                    -- sirf pehli image
  first_seen_at  DATE NOT NULL,            -- naye products isse
  last_seen_at   DATE NOT NULL,            -- hataye gaye isse
  is_active      BOOLEAN NOT NULL DEFAULT true,
  UNIQUE (store_id, handle)
);

4 · variants

CREATE TABLE variants (
  id             BIGSERIAL PRIMARY KEY,
  product_id     BIGINT NOT NULL REFERENCES products(id) ON DELETE CASCADE,
  sku            TEXT,
  option1_name   TEXT,  option1_value  TEXT,     -- Size
  option2_name   TEXT,  option2_value  TEXT,     -- Color
  option3_name   TEXT,  option3_value  TEXT,     -- Fabric
  variant_image  TEXT,
  variant_key    TEXT NOT NULL,      -- sku, ya options ka combo agar sku na ho
  first_seen_at  DATE NOT NULL,
  last_seen_at   DATE NOT NULL,
  is_active      BOOLEAN NOT NULL DEFAULT true,
  UNIQUE (product_id, variant_key)
);
✕ SKU par akela bharosa mat karein

Aapki file mein 52 duplicate SKUs hain (114 rows). Misal ke taur par MKS-EMB26-017-Cream 4 baar aata hai. Isi liye variant_key banaya hai — SKU + options ka combo. Warna variants aapas mein gaddmadd ho jayenge.

5 · variant_history — append-only

CREATE TABLE variant_history (
  id                BIGSERIAL,
  variant_id        BIGINT NOT NULL REFERENCES variants(id) ON DELETE CASCADE,
  scrape_run_id     BIGINT NOT NULL REFERENCES scrape_runs(id),
  observed_date     DATE NOT NULL,
  price             NUMERIC(12,2),
  compare_at_price  NUMERIC(12,2),
  discount_pct      NUMERIC(5,2) GENERATED ALWAYS AS (
                      CASE WHEN compare_at_price > 0 AND compare_at_price > price
                           THEN ROUND((compare_at_price - price) / compare_at_price * 100, 2)
                           ELSE 0 END
                    ) STORED,
  inventory_policy  TEXT,
  inventory_qty     INT,
  in_stock          BOOLEAN,
  change_type       TEXT,   -- new | price_up | price_down | stock_in | stock_out | removed
  raw               JSONB,  -- poori original row, zaroorat pare to
  PRIMARY KEY (id, observed_date)
) PARTITION BY RANGE (observed_date);

-- har mahine ki apni partition — purana data alag rehta hai, queries tez
CREATE TABLE variant_history_2026_08 PARTITION OF variant_history
  FOR VALUES FROM ('2026-08-01') TO ('2026-09-01');

Storage — ek ahem faisla

Aapne kaha tha "har scrape naya entry ban kar save ho." Lafzi tor par iska matlab:

TareeqaRows / dinRows / saalFaisla
Har variant, har din (full snapshot)~500,000~180,000,000✕ Bewajah bhaari
Sirf jo badla (change-only)~15,000~5,500,000✓ Yehi karein
✓ Change-only se bhi sab kuch milta hai

"Aaj kya badla?" → variant_history WHERE observed_date = today
"Naya kya aaya?" → products WHERE first_seen_at = today
"Scrape chala tha?" → scrape_runs
"12 March ko rate kya tha?" → us date tak ki aakhri history row

Wahi jawab, magar 3% storage mein — aur teesre saal bhi report utni hi tez chalegi.

07Report Query

Ek hi query — yehi screen ko bhi feed karti hai aur PDF ko bhi. Alag alag logic likhne ki zaroorat nahi.

SELECT p.handle, p.title,
       v.option1_value AS size,
       v.option2_value AS color,
       h.observed_date, h.price, h.compare_at_price,
       h.discount_pct, h.in_stock,
       h.price - LAG(h.price) OVER w   AS price_change,
       h.in_stock <> LAG(h.in_stock) OVER w AS stock_flipped
FROM   variant_history h
JOIN   variants v ON v.id = h.variant_id
JOIN   products p ON p.id = v.product_id
WHERE  p.store_id = $1                          -- card se aaya
  AND  h.observed_date BETWEEN $2 AND $3        -- date filter se aaya
WINDOW w AS (PARTITION BY h.variant_id ORDER BY h.observed_date)
ORDER BY p.handle, v.id, h.observed_date;

LAG() automatically pichli row utha leta hai — isi liye din-ba-din ka comparison khud ba khud ho jata hai. MongoDB mein ye khud likhna parta.

09Warnings — CSV se milne wale masail

Ye teen cheezein build shuru karne se pehle hal karni hain. Sample file (Alkaram, 27 Jul 2026) ke analysis se nikli hain.

✕ 1 — Stock ka data hai hi nahi

Aapki file mein Inventory quantity ki 1,922 rows hain aur sab ki value 0. Total units = 0.

Yani sirf is column par bharosa karenge to system kahega "saara store out of stock hai" — jo bilkul ghalat hoga. Aur stock in/out aapki core requirement hai.

Hal: stock aise nikalein —

Variant aaj ke CSV mein maujood hai      →  IN STOCK
Kal tha lekin aaj gayab hai              →  OUT OF STOCK

Shopify stores mein aksar sold-out variant feed se hat jata hai. Isi liye last_seen_at column banaya hai — wahi asal stock signal hai, Inventory quantity nahi.

⚠ 2 — Pehle 2–3 aur stores check karein

Agar un stores ki CSV mein Inventory quantity ke asli numbers hain, to wo use kar lenge. Agar wahan bhi 0 hai, to last_seen_at wala tareeqa final hai. Ye ingest logic likhne se pehle confirm karna zaroori hai.

⚠ 3 — Duplicate SKUs

52 duplicate SKUs, 114 rows par asar. Misal: MKS-EMB26-017-Cream 4 baar. Isi liye variant_key = SKU + options ka combo banaya hai. Sirf SKU par bharosa karenge to variants gaddmadd ho jayenge.

Choti cheezein

MaslaKitnaKya karein
Type inconsistent—SHIRT, TROUSER & DUPATTA vs SHIRT , TROUSER & DUPATTA — ingest par normalize karein
Tags case duplicate—ESSENTIALS / Essentials — lowercase kar ke store karein
Vendor field kharab12 rowsSHIRT COLLAR, Slim Fit — validate karein

✓ Agla qadam

1. 2–3 aur stores ki CSV le kar Inventory quantity confirm karein.
2. Drive par file naming ka pattern tay karein — sample file (https___www_alkaramstudio_com__shopify 27_07_26.csv) mein domain aur date dono maujood hain, ye theek hai. Baaki 99 stores bhi isi pattern mein aane chahiyen.
3. Approach 1 par migrations likh kar ingest shuru karein.
