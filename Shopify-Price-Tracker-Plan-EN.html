01Project Flow

A Google Sheet holds 100 store URLs. Every day each store produces one CSV. From those files we extract price, discount and stock changes — at variant level (size / color), not just product level.

1
Phase 1 — UiPath
Reads the 100 store URLs from the Google Sheet, downloads each store's CSV, and uploads them to Google Drive. Runs automatically every day.
2
Phase 2 — Ingest Worker
Picks up new files from Drive, parses each CSV, extracts only the 18 columns we need, and writes them into the database. Every file is logged in scrape_runs.
3
Phase 2 — Diff Engine
Compares today's data against yesterday's and writes only what changed into history — price up/down, stock in/out, new product, removed product.
4
PostgreSQL
Five tables. handle is the unique ID — not the title, since titles repeat. Full history is preserved.
5
Frontend — Next.js
Log in → 100 store cards → click a card → that store's report (charts + variant table) → date-range filter → PDF download.

✓ Recommendation — start with Approach 1

1. You need store cards and a custom PDF — Approach 3 simply cannot deliver those.
2. Approach 2 is more robust but not needed yet. 100 files a day is a small load; taking on server maintenance now buys nothing.

03Database Choice

Decision: PostgreSQL (relational). Not a vector database.

DatabaseVerdictReason
PostgreSQL✓ Use thisNumbers, dates and exact comparison — all native. The source data is already tabular.
MongoDB⚠ Not neededWould work, but day-over-day comparison has to be hand-written. Extra effort for no gain.
Vector DB✕ Do not useIt cannot detect a price change at all. See the example below.

Why a vector DB fails here — a real example

A vector database answers exactly one kind of question: "what is semantically similar to this?" It searches by meaning. It does not compare exact numbers.

Take a real variant from your own file:

Yesterday :  SS-59.1-25-3-Blue  |  price 3,432  |  compare_at 4,290  |  in stock
Today     :  SS-59.1-25-3-Blue  |  price 3,290  |  compare_at 4,290  |  out of stock

This is what must be caught →  142 PKR drop, discount 20% → 23.3%, and a stock-out
✕ Where the vector DB breaks

Embed those two lines and their vectors land on top of each other — cosine similarity ≈ 0.999. The database reports "these are the same thing." It has no way to see the difference between 3,432 and 3,290, because the shirt, the color and the name are all identical.

There is a second problem: vector search is approximate by design. There is no guarantee every match is returned. You need a daily report people can trust — if three stores' price drops go missing, the report is worthless.

The same job in SQL

One line. Exact, complete and fast:

WHERE today_price < yesterday_price
QuestionPostgreSQLVector DB
Which products dropped in price?✓ One query✕ Impossible
Which variants went out of stock?✓ One query✕ Impossible
Report for 1 July – 27 July✓ BETWEEN✕ No concept of dates
Which products are new?✓ One query✕ Impossible
"Find products similar to this one"Difficult✓ Excellent
ℹ When a vector DB would earn its place

Later, when you want to match the same product across different stores — for example "Blue Printed Lawn 3-Piece" vs "3 PC Lawn Suit — Blue" (different names, same item). But you have scoped that out for now: no cross-store comparison yet. So park it.

Good news: Postgres already ships pgvector. When the need arrives, enable it in the same database. No migration required.

ℹ Why "independent" still holds

Independence is about behaviour, not storage. Each store gets its own scrape_runs row and its own ingest job, so one store failing never touches the other 99. Each report filters by store_id. Postgres Row Level Security can enforce that boundary at the database level if you ever need a hard guarantee.

And the decisive point: all 100 CSVs have the identical 49-column Shopify shape. Same shape means same table. Separate tables would only make sense if each store had a different format.

✓ This is the standard pattern

It is called multi-tenancy, and effectively every SaaS product is built this way — including Shopify itself, which holds millions of stores in shared tables keyed by shop ID. At 100 stores × ~5,000 variants = 500,000 rows, this is a small workload for Postgres.

06How Versioning Works

The core of the system. Every day's CSV is compared against the previous day, and only what changed is recorded — yet the complete state of any past date can still be reconstructed exactly.

6.1 · Two layers

The whole design rests on splitting the data into two layers that do different jobs and never fight each other.

Layer 1

Current state

products · variants
  • What the store looks like today
  • handle, title, SKU, size, color, fabric
  • current_price, current_in_stock — a cache for speed
  • first_seen_at, last_seen_at, is_active
↻ Updated in place every day
Layer 2

History

variant_history
  • What happened, and when
  • price, compare-at, discount %, stock
  • previous values carried on the same row
  • one row per actual change, with its date
＋ Append-only · never updated, never deleted
ℹ The division of labour

Layer 1 answers "what is the price right now?" in one indexed row read — that is what the ingest diff and the store cards use. Layer 2 answers "what was the price on 14 May?" and "when did it change?". Neither can overwrite the other, because price only ever changes in Layer 2 by adding a row.

6.2 · The daily loop

This runs once per store, per day. Identical for all 100 stores.

1
Open a scrape run
Insert a scrape_runs row with status pending — proof this store was attempted today.
2
Parse today's CSV
Build a set keyed by (handle, variant_key) holding price, compare-at price and presence.
3
Read yesterday's state
Load the store's active variants with their current_* values. No history scan — one indexed read.
4
Compare, variant by variant
In CSV but not in DB → new
In both, price / compare-at / stock differs → write a history row
In both, everything identical → update last_seen_at only
In DB but not in CSV → stock_out (or removed if the whole handle is gone)
5
Refresh the cache
Overwrite current_price, current_in_stock, last_seen_at on Layer 1.
6
Close the run
Set status success and record the counts — products found, changes written.
↻ Tomorrow's CSV runs the same six steps against today's state
✕ The one rule that must never be broken

If the download failed, or the file came back empty or truncated, skip step 4's removal detection entirely. Otherwise one bad download marks 2,000 products as removed and corrupts the history permanently.

Guard it with a sanity check: if today's product count is below 50% of yesterday's, mark the run partial, skip removals, and raise an alert. A store never loses half its catalogue overnight — that is a scrape problem, not a store event.

6.4 · So does the old price get overwritten?

✓ Yes in Layer 1 — no in Layer 2

variants.current_price goes from 3,000 to 2,500. That is deliberate: it is a cache so the app can show today's price without scanning history.

variant_history still holds 3,000 against 01-Aug, and always will. The new value arrived as a row beneath the old one, not on top of it.

If the cache is ever wrong or lost, it can be rebuilt from history in one statement — so nothing authoritative depends on it.

-- rebuilding the Layer 1 cache from Layer 2, if ever needed
UPDATE variants v
   SET current_price = h.price, current_in_stock = h.in_stock
  FROM (SELECT DISTINCT ON (variant_id) variant_id, price, in_stock
          FROM variant_history ORDER BY variant_id, observed_date DESC) h
 WHERE h.variant_id = v.id;
ℹ Make it impossible to overwrite history

Lock it at the database level so no bug can ever rewrite the past:

REVOKE UPDATE, DELETE ON variant_history FROM app_user;
GRANT  INSERT, SELECT  ON variant_history TO   app_user;

6.5 · The seven event types

Every change written to history is exactly one of these.

new
Handle or variant appeared in a CSV for the first time ever.
price_down
Selling price fell. Amount and % both recorded.
price_up
Selling price rose.
discount_change
Price unchanged, but compare-at moved — so the advertised % changed.
stock_out
Variant vanished from the CSV while its product is still listed.
stock_in
A previously missing variant reappeared.
removed
The whole handle left the store. Row kept, is_active=false.
— no row —
Nothing differed. Only last_seen_at advances.
⚠ discount_change is easy to miss

A store can leave the price at 3,432 and raise the compare-at price from 4,290 to 4,990. The customer now sees 31.2% off instead of 20.0% — with no price movement at all. That is why compare_at_price is compared alongside price, not derived from it.

6.7 · Reading any past date

To recover the state on a given day, take the last row on or before that date. In SQL that is one DISTINCT ON.

SELECT DISTINCT ON (variant_id)
       variant_id, observed_date, change_type,
       price, compare_at_price, discount_pct, in_stock
FROM   variant_history
WHERE  variant_id = 4471
  AND  observed_date <= '2026-08-01'      -- ← any date you want
ORDER  BY variant_id, observed_date DESC;

Every day answered correctly, from five rows. This pattern has a name — Slowly Changing Dimension Type 2 — and it is how banking and inventory systems have kept history for decades.

Wrap it in a function so nobody rewrites it

CREATE OR REPLACE FUNCTION store_state_on(p_store_id BIGINT, p_date DATE)
RETURNS TABLE (variant_id BIGINT, handle TEXT, title TEXT, sku TEXT,
               variant_label TEXT, price NUMERIC, compare_at NUMERIC,
               discount_pct NUMERIC, in_stock BOOLEAN, changed_on DATE) AS $$
  SELECT DISTINCT ON (h.variant_id)
         h.variant_id, p.handle, p.title, v.sku,
         concat_ws(' / ', v.option1_value, v.option2_value, v.option3_value),
         h.price, h.compare_at_price, h.discount_pct, h.in_stock, h.observed_date
  FROM   variant_history h
  JOIN   variants v ON v.id = h.variant_id
  JOIN   products p ON p.id = v.product_id
  WHERE  p.store_id = p_store_id
    AND  h.observed_date <= p_date
  ORDER  BY h.variant_id, h.observed_date DESC;
$$ LANGUAGE sql STABLE;

-- the whole store, as it stood on any date
SELECT * FROM store_state_on(12, '2026-08-01');   -- day 1
SELECT * FROM store_state_on(12, '2026-08-12');   -- day 12

Comparing any two dates

SELECT d1.handle, d1.sku, d1.variant_label,
       d1.price  AS day_1_price,
       d12.price AS day_12_price,
       d12.price - d1.price AS diff,
       ROUND((d12.price - d1.price) / NULLIF(d1.price,0) * 100, 2) AS diff_pct,
       d1.in_stock AS stock_before, d12.in_stock AS stock_after
FROM      store_state_on(12, '2026-08-12') d12
FULL JOIN store_state_on(12, '2026-08-01') d1 USING (variant_id)
WHERE  d1.price    IS DISTINCT FROM d12.price
   OR  d1.in_stock IS DISTINCT FROM d12.in_stock;

FULL JOIN is deliberate — it also surfaces variants that did not exist on day 1 (new) and ones gone by day 12 (removed).

ℹ Two different reads — do not confuse them

Ingest compares against variants.current_* — one indexed row, milliseconds, no history touched. That keeps 100 stores ingesting fast.
Reporting reads variant_history — that is where six-month-old answers come from.

6.8 · How history reaches the report

Reports never join three tables by hand. One view does it once, and the screen, the PDF and the CSV export all read from it.

CREATE VIEW v_change_report AS
SELECT s.id AS store_id, s.name AS store_name,
       p.handle, p.title, p.vendor, p.product_type, p.image_src,
       'https://' || s.domain || '/products/' || p.handle AS product_url,
       v.sku, concat_ws(' / ', v.option1_value, v.option2_value, v.option3_value) AS variant_label,
       h.observed_date, h.change_type,
       h.prev_price, h.price, h.price - h.prev_price AS price_diff,
       ROUND((h.price - h.prev_price) / NULLIF(h.prev_price,0)*100, 2) AS price_diff_pct,
       h.prev_compare_at_price, h.compare_at_price, h.discount_pct,
       h.prev_in_stock, h.in_stock,
       p.first_seen_at, v.last_seen_at
FROM   variant_history h
JOIN   variants v ON v.id = h.variant_id
JOIN   products p ON p.id = v.product_id
JOIN   stores   s ON s.id = p.store_id;

-- the entire report is then this
SELECT * FROM v_change_report
WHERE  store_id = 12 AND observed_date BETWEEN $1 AND $2
ORDER  BY observed_date DESC, handle;

✓ Summary — the versioning rules in five lines

1. handle identifies a product forever; variant_key identifies a variant.
2. Layer 1 (variants) is overwritten daily and holds only "now".
3. Layer 2 (variant_history) is append-only and holds "when". Nothing in it is ever updated or deleted.
4. A row is written only when price, compare-at price or stock differs — each row means "this held until the next row".
5. Any past date is recovered with DISTINCT ON … WHERE observed_date <= $date.

Without it there is no way to know which store's scrape failed. Users will read stale data as if it were current — and silent scrape failures are exactly how a daily-report system loses trust.

5 · variant_history — append-only

CREATE TABLE variant_history (
  id                BIGSERIAL,
  variant_id        BIGINT NOT NULL REFERENCES variants(id) ON DELETE CASCADE,
  scrape_run_id     BIGINT NOT NULL REFERENCES scrape_runs(id),
  observed_date     DATE NOT NULL,
  price             NUMERIC(12,2),
  compare_at_price  NUMERIC(12,2),
  discount_pct      NUMERIC(5,2) GENERATED ALWAYS AS (
                      CASE WHEN compare_at_price > 0 AND compare_at_price > price
                           THEN ROUND((compare_at_price - price) / compare_at_price * 100, 2)
                           ELSE 0 END
                    ) STORED,
  inventory_policy  TEXT,
  inventory_qty     INT,
  in_stock          BOOLEAN,

  -- previous values carried on the same row, so reports need no LAG()
  prev_price             NUMERIC(12,2),
  prev_compare_at_price  NUMERIC(12,2),
  prev_in_stock          BOOLEAN,

  change_type       TEXT,   -- new | price_up | price_down | stock_in | stock_out | removed
  raw               JSONB,  -- the original row, kept for escape hatches
  PRIMARY KEY (id, observed_date)
) PARTITION BY RANGE (observed_date);

-- one partition per month — old data stays separate, queries stay fast
CREATE TABLE variant_history_2026_08 PARTITION OF variant_history
  FOR VALUES FROM ('2026-08-01') TO ('2026-09-01');

Storage — one decision worth flagging

You asked that "every scrape should be saved as a new entry." Taken literally, that means:

StrategyRows / dayRows / yearVerdict
Every variant, every day (full snapshot)~500,000~180,000,000✕ Wasteful
Only what changed (change-only)~15,000~5,500,000✓ Do this
✓ Change-only still answers every question

"What changed today?" → variant_history WHERE observed_date = today
"What's new?" → products WHERE first_seen_at = today
"Did the scrape run?" → scrape_runs
"What was the price on 12 March?" → the last history row on or before that date

Same answers at roughly 3% of the storage — and reports stay fast into year three.

09Report Query

A single query feeds both the screen and the PDF. No duplicated logic.

SELECT p.handle, p.title,
       v.option1_value AS size,
       v.option2_value AS color,
       h.observed_date, h.price, h.compare_at_price,
       h.discount_pct, h.in_stock,
       h.price - LAG(h.price) OVER w   AS price_change,
       h.in_stock <> LAG(h.in_stock) OVER w AS stock_flipped
FROM   variant_history h
JOIN   variants v ON v.id = h.variant_id
JOIN   products p ON p.id = v.product_id
WHERE  p.store_id = $1                          -- from the card click
  AND  h.observed_date BETWEEN $2 AND $3        -- from the date filter
WINDOW w AS (PARTITION BY h.variant_id ORDER BY h.observed_date)
ORDER BY p.handle, v.id, h.observed_date;

LAG() pulls the previous row automatically, so day-over-day comparison comes for free. In MongoDB this has to be written by hand.

11Warnings — Issues Found in the CSV

Three things to resolve before development starts. All come from analysing the sample file (Alkaram, 27 Jul 2026).

✕ 1 — There is no stock data

In your file, Inventory quantity has 1,922 rows and every one of them is 0. Total units = 0.

Relying on that column alone would make the system report "the entire store is out of stock" — which is plainly wrong. And stock in/out is a core requirement.

The fix — derive stock like this:

Variant present in today's CSV        →  IN STOCK
Present yesterday but missing today   →  OUT OF STOCK

In most Shopify stores a sold-out variant drops out of the feed entirely. That is why last_seen_at exists — it is the real stock signal, not Inventory quantity.

⚠ 2 — Verify against two or three more stores first

If their CSVs carry real numbers in Inventory quantity, use that instead. If those are zero too, the last_seen_at approach becomes final. Confirm this before writing the ingest logic.

⚠ 3 — Duplicate SKUs

52 duplicate SKUs affecting 114 rows. Example: MKS-EMB26-017-Cream appears four times. That is why variant_key combines SKU with the option values. Keying on SKU alone would merge distinct variants.
